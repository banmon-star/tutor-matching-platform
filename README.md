家教撮合平台 MVP｜Tutor Matching Platform

产品经理作品集项目：将微信群/私聊驱动的家教中介流程，抽象为可执行的订单、候选、遴选、权限与退款状态。

🌐 在线作品集：
https://banmon-star.github.io/tutor-matching-platform/

项目定位

这是一个围绕家教撮合场景设计并实际跑通的 MVP，包含：

家长端（微信小程序）：发布需求、查看订单、比较候选教员、完成遴选

教员端（微信小程序）：提交简历、接单、支付信息费、进入候选池、查看入选/退款结果

管理后台（Web）：教员审核、订单审核、付款核验、退款管理、数据概览

业务后端：FastAPI + MySQL，负责状态流转、权限与数据持久化

当前阶段：MVP / 内部体验验证 / 产品经理作品集 Demo
不将本地演示版本包装为已商业化上线产品。

为什么做这个产品

传统家教中介常见流程：

家长发需求 → 中介整理 → 群内发单 → 教员报名 → 收信息费 → 人工筛选 → 家长选择 → 发联系方式 → 未入选退款

这套流程可以运转，但存在明显问题：

需求、简历、报名信息分散在聊天记录中

谁已付款、谁进入候选、谁被选中高度依赖人工记录

家长缺乏统一的候选人比较入口

联系方式开放时机不清晰，容易造成骚扰或绕平台

未入选退款缺乏统一的状态与后台处理流程

因此，我把原本依赖人工经验的流程抽象为：

对象 + 状态 + 规则 + 权限

核心业务流程

家长发布需求
    ↓
管理员审核
    ↓
教员浏览并报名
    ↓
信息费付款 + 后台核验
    ↓
进入候选池
    ↓
家长比较候选教员
    ↓
家长最终选择
   ↙            ↘
已入选          未入选
↓               ↓
联系方式解锁      退款资格开放

三个关键产品设计

1. 候选池机制

教员付款成功后并不直接获得家长联系方式，而是获得“候选资格”。

这样可以：

避免多个教员同时骚扰家长

让家长保留最终选择权

将人工候选名单变成结构化业务关系

为后续状态、权限与退款提供统一依据

2. 联系方式延迟解锁

联系方式不是普通展示字段，而是由业务状态控制的权限。

未入选：不可查看

候选中：不可查看

家长完成最终遴选：仅被选中教员可查看

3. MVP支付取舍

首版没有直接接入正式支付接口，而采用：

展示收款码 → 教员付款 → 上传截图 → 后台人工核验

原因是 MVP 首先验证：

三方撮合业务能否在线上完整跑通？

而不是优先投入复杂支付基础设施。

状态机设计

订单侧

待审核 → OPEN → CANDIDATES → SELECTED

教员报名侧

待付款核验 → 候选中 → 已入选 / 未入选 → 退款中 → 已退款

状态会直接影响：

页面按钮

联系方式访问权限

退款资格

后台待办

数据统计

一个按钮背后的系统联动

“家长选择一名教员”看起来只是一次点击，但实际需要同时处理：

更新订单状态

更新被选中教员候选关系

标记其他候选未入选

解锁被选中教员的联系方式权限

开放其他候选的退款资格

同步管理后台状态

这也是该项目中我认为最有价值的产品抽象之一。
