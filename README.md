# 家教撮合平台 MVP｜Tutor Matching Platform

> 将微信群/私聊驱动的家教中介流程，抽象为可执行的订单、候选、遴选、权限与退款状态。

## 项目简介

这是一个面向家教撮合场景的产品 MVP，包含：

- **家长端（微信小程序）**：发布家教需求、查看订单、比较候选教员、完成最终遴选
- **教员端（微信小程序）**：提交简历、审核后接单、支付信息费、进入候选池、查看入选/退款结果
- **管理后台（Web）**：教员审核、订单审核、付款核验、退款管理、收款码设置、数据概览
- **后端服务（FastAPI + MySQL）**：负责业务规则、状态流转、权限控制与数据持久化

项目当前定位为 **产品经理作品集 / MVP业务验证 Demo**，不是线上商用系统。

---

## 为什么做这个产品

传统家教中介常见流程：

`家长发需求 → 中介整理 → 群内发单 → 教员私聊 → 收信息费 → 人工筛选 → 家长选择 → 发联系方式 → 未入选退款`

主要问题：

1. 需求字段不统一，中介反复确认
2. 教员简历缺乏标准化审核
3. 报名、付款、候选关系依赖人工记录
4. 联系方式过早开放会带来骚扰和绕平台风险
5. 未入选退款容易形成售后管理负担
6. 中介缺乏统一运营后台和业务状态视图

因此，我将原本依赖人工经验的撮合流程拆解为：

> **对象 + 状态 + 规则 + 权限**

## 核心产品流程

```text
家长发布需求
    ↓
管理员审核并上架
    ↓
审核通过的教员浏览订单
    ↓
教员报名 + 信息费核验
    ↓
进入候选池
    ↓
家长比较候选教员
    ↓
家长选择 1 名教员
   ↙              ↘
入选教员          未入选教员
联系方式解锁       获得退款资格
                      ↓
                   退款闭环
```

## 最重要的三个产品设计

### 1. 候选池机制

教员付款成功后**不直接获得家长联系方式**，而是进入候选池。

目的：

- 避免多个教员同时骚扰家长
- 让家长拥有最终选择权
- 保持平台对撮合过程的控制
- 将人工候选名单变成结构化业务关系

### 2. 联系方式延迟解锁

联系方式只有在家长完成最终遴选后，才向被选中的教员开放。

这不是一个单纯的“字段隐藏”，而是由订单/候选状态共同决定的**权限机制**。

### 3. MVP支付取舍

第一版没有直接接入复杂支付接口，而是：

`展示收款码 → 教员转账 → 上传截图 → 后台人工核验`

原因是 MVP 首先验证：

> “三方撮合业务能否在线上完整跑通？”

而不是优先投入支付基础设施。

## 信息费规则

当前 MVP 将信息费规则结构化为可计算逻辑：

- 每周 1 次：`1.5 × 单次课费`
- 每周 2 次：`一周课费 × 100%`
- 每周 3 次：`一周课费 × 80%`
- 每周 4–5 次：`一周课费 × 70%`
- 每周 6 次及以上：`一周课费 × 60%`
- 网课：对应线下信息费 `× 1.2`
- 月薪制：月薪 `× 20%`

规则在后端独立封装并保留规则版本，便于后续迭代。

## 产品状态设计

### 需求侧

`待审核 → 已上架/报名中 → 遴选中 → 已完成`

### 教员报名侧

`未报名 → 待付款核验 → 候选中 → 已入选 / 未入选 → 退款中 → 已退款`

状态决定：

- 页面展示
- 操作按钮
- 联系方式权限
- 退款资格
- 后台待办

## 项目收获

这个项目让我从“页面功能思维”转向了更系统的：

> **对象 + 状态 + 规则 + 权限 + 异常**

例如“家长选择一个教员”看似只是一次点击，实际会同时影响：

- 订单状态
- 候选关系
- 被选中教员结果
- 未入选教员退款资格
- 联系方式访问权限
- 后台业务数据
